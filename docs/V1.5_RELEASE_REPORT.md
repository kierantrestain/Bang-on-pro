# Bang On Pro V1.5: four reasoning providers with failover, and a department that learns (internal pre-release)

**Branch:** `claude/optimistic-shannon-o50tdx`, built on the V1.4 checkpoint `3c95efb`. Both V1.4 CI runs on that checkpoint passed: Linux [45761103670](https://github.com/kierantrestain/Bang-on-pro/actions/runs/45761103670) and the macOS DMG [45761052484](https://github.com/kierantrestain/Bang-on-pro/actions/runs/45761052484). Neither showed a release-blocking V1.4 issue.

**Development:** done by one lead engineer. No development agents were spawned. Research repositories were read for patterns only and no code was copied ([working notes](V1.5_WORKING_NOTES.md)).
There are no new dependencies (stdlib `sqlite3`), no models, no services and no vector database. The editing software, its interface and the 14 agents are unchanged except for the additions below.

**Evidence labels, kept apart:**
- **Live:** an authenticated Claude Code CLI using the account's own sign-in.
- **Mocked provider responses:** fake `claude`, `codex`, `grok` and `agy` executables that speak each CLI's documented output.
- **Mocked reasoning:** scripted plans.
- **Real draft:** every claim is checked on the replayed draft and the written `.kdenlive` project by the independent QC checks.
- **Synthetic footage:** a generated three-camera podcast without words.

No real production was run and no editor took part.

## Delivered, in implementation order

| Milestone | What works | Where |
|---|---|---|
| 1. Four providers, shared budget, automatic failover | **Adapters** for Claude Code (`claude -p --output-format json`), Codex (`codex exec --sandbox read-only`), Grok Build (`grok -p --output-format json`, tools denied) and Antigravity (`agy -p --output-format json`, with a pseudo-terminal fallback). All four can be authorised at once, in a priority order you set.<br>**Failures are classified** as usage exhausted, rate limited, unavailable, authentication, not entitled, incompatible CLI, invalid request or unusable output. Only availability problems fail over. Authentication, entitlement and incompatibility problems park that provider until you re-authorise it.<br>**Cooldowns** use the reported reset (`limit reached\|epoch`, *try again in 2 hours 5 minutes*, *Retry-After*, ISO time, *resets 3pm*) or a default. There is no polling. The preferred provider comes back at the next task boundary.<br>**One budget** per task and per day covers every provider, agent and purpose, failed attempts included. A local ledger records the reported usage, or `unknown`. API-key variables are stripped unless you opted into API billing. | `mcp/reasoning.py` |
| 1b. No lost or repeated work | The cycle checkpoints the plan, the applied steps, the in-flight step and the provider events inside the task. The next provider receives the project pack, *already done and verified* and *what failed*; it never receives a conversation history.<br>When no provider is available, the task is **blocked** and nothing is half-done. A **cancelled** task stops between steps. A **crashed** task with an edit already written recognises that edit. `resume` continues any of them in a new process. | `mcp/execution.py` |
| 2. Experience capture and scoped knowledge | A SQLite store (WAL). When a task completes, its evidence is written in one idempotent, sanitised transaction: instruction, compound tool calls, verified edits, rejected edits, QC findings and corrections, checks, outcome and usage. Your approvals and rejections and draft-vs-final differences come from the existing preference store.<br>**Six knowledge categories** are scoped global, format, series, episode and specialist. Each row records provenance, confidence, support and contradictions, a value histogram for conflicts, a version and its history. Retrieval is bounded (1,600 chars); the most specific scope wins and other series are never seen. A lesson that two series learn independently becomes format knowledge. | `department/intelligence.py` |
| 3. Reusable skills | A verified task built from compound tools is generalised into a declarative workflow. Concrete values become anchors: turn role, rank and point; camera role; speaker role; asset input. The workflow is validated strictly: allowlisted tools and arguments, no paths, no code, at most 12 steps, combined skills at most 2 deep.<br>Lifecycle: tried on the next production before any reasoning call → *validated* once QC verifies it on another production → *active* → *retired* after repeated failures. A failed skill run is undone and the task goes to reasoning. | `department/skills.py` |
| 4. Bounded strategy optimisation | Whitelisted, bounded settings per specialist (Graphics: strap duration, speaker alignment, default fade, position; Multicamera Director: shortest reaction).<br>**Propose:** each validated failure lesson suggests a candidate, plus at most one optional reflective LLM proposal from the shared budget. **Test:** baseline and candidate run identical scenario steps on the same draft **in memory** (nothing is written), split into learning, validation and held-out sets, and the independent `check_draft` scores them. **Decide:** promote only on a held-out gain, with no validation or learning regression, no new error-severity defect and no unjustified extra operations. Procedural changes are promoted automatically when allowed; subjective ones wait for you.<br>**Monitor:** a confirmed production regression (≥2 tasks, ≥0.4 more defects per task than the parent) reverts automatically. Every version is kept, with promotion and rollback history. | `department/strategies.py` |
| 5. Controls and UI | `bop_learn` (MCP) and `python -m bangonpro.ai_engine.mcp learn ACTION` provide status, lessons, skills, strategies, performance, history, optimise, approve, reject, disable, enable, rollback, settings (enabled, scope, retention, auto-promotion, trial skills), export and forget. `providers [--priority] [--test]` and `resume` are new CLI commands.<br>The Agent Control Centre header tooltip shows the provider order, the active provider, the last switch and a learning summary. Strategies awaiting approval appear under the Learning Agent in Review. There is no new panel. | `department/learning_controls.py`, `AgentControlCentre.{h,cpp}` |

## Evidence

### 1. Live authenticated runs (Claude Code, app-driven through the router)

The instruction was *"Give the guest's longest answer a listening cutaway: show the host for about a second and a half in the middle of it, and hold an Episode 12 card over the first two seconds of the show"*. The rules did not understand it, no skill matched, and the router used Claude.

| Run | Result | What it found |
|---|---|---|
| [1](evidence/v1.5/live_claude_app_driven_run1.json) | Edits correct and verified. Status `needs_attention` | **Defect:** Claude wrote six checks with `t` instead of `time`; the in-app cycle kept them as failed checks. **Fixed:** planner checks are validated, rejected with a reason, fed back and reported; each check's keys are in the prompt; `bop_task` rejects unknown keys |
| [2](evidence/v1.5/live_claude_app_driven_run2.json) | Checks well formed and passing. One unresolved item | **Defect:** QC did not treat the stated *"Listening cutaway"* as deliberate and switched it back. Claude redid it and locked the range. **Fixed:** QC recognises deliberate cutaways (react, listen, cutaway, insert, response, noddy) |
| [3](evidence/v1.5/live_claude_app_driven_run3.json) | **Verified**, 1 planning call, 30 s, reported $0.11, 0 QC corrections, 0 unresolved | Host cutaway at 14.5–16.0 s, the guest's strap shortened so it is not over the host, Episode 12 card at 0–2 s. 16 evidence rows captured |

Each fix has a regression test. Total live usage reported by the CLI was about $0.72 (7 calls), against the account's subscription.

### 3. Learning from a verified mistake, applied in the next episode ([evidence](evidence/v1.5/lesson_transfer.json); mocked reasoning, synthetic footage)

Held-out score went from −1.50 to −1.00 and corrections needed per scenario from 0.50 to 0.00. Validation went from −1.0 to 0.0. Operations and time were unchanged. It was promoted as procedural.

### 4. A reusable native editing skill ([evidence](evidence/v1.5/skill_reuse.json))

Episode 1 used a scripted plan: "cut to the host listening in the middle of the guest's longest answer". It became `bop_switch_camera` with start `{turn: guest, longest, mid, −0.75}`, end `+1.5`, camera `{role: host}`.
Episodes 2 and 3 had **no plan available**. The skill ran and QC verified it on the draft, with **0 reasoning calls**. Its status went candidate → validated → active. A copy that names a missing camera role is not applicable.

### 5. Degraded strategy rejected and a regressing promotion rolled back ([evidence](evidence/v1.5/degraded_strategy.json))

- **Degraded candidate** (straps held 1 s): rejected with *"no improvement on held-out scenarios (−1.50 vs −1.50)"*.
- **Forced regressing promotion** (1.2 s): its two production tasks each needed a QC correction, 1.0 defect per task against 0.5 on the parent. It was **reverted automatically** to version 0. History: proposed, rejected, proposed, promoted, rolled_back, rollback. The editor's controls (inspect, manual rollback, settings, export, approval refused for an untested candidate) were exercised through `bop_learn` with the strict MCP schema.

### 6. Persistence, isolation, conflicts and malicious inputs (no media)

- Knowledge survives a new connection.
- A conflict of 4.0, 4.0 and 3.0 resolves to 4.0, with 1 contradiction recorded and version 3.
- Series isolation holds, and promotion to format knowledge happens only after two independent series.
- Retrieval stays within its budget.
- Credentials, prompts and private paths are stripped from evidence, and re-recording is idempotent.
- Skill specs with unknown tools, extra arguments, paths, `$eval`, unknown agents, bad skill references or extra fields are refused.
- Strategy settings outside the whitelist or bounds are refused, and subjective settings are classed as needing approval.
- Export by series, forget by series, and disabling learning all work.

## Not done or limited (explicit)

- **Only Claude Code was tested live.** Codex, Grok Build and Antigravity are implemented against their documented headless modes and tested with mocked responses only; their CLIs are not installed here. Antigravity's JSON field names and its terms for account-based orchestration are unconfirmed.
- **Self-improvement is demonstrated on synthetic footage with scripted plans.** The measured improvements are real measurements of the draft, but the scenarios are synthetic. Human editing minutes are not measured: performance reports them as `unknown (not recorded)`. No improvement on real productions is claimed.
- **The strategy space is deliberately small:** five settings for two specialists. Other specialists learn lessons (retrieved into their context) and skills, but they have no tunable strategy settings yet.
- **Skills come only from compound-tool tasks.** A task that includes low-level `bop_edit` operations, like live run 3, is captured as experience but not generalised.
- **Reflective LLM proposals are implemented but optional and untested live;** deterministic reflection from lessons is the tested path.
- Claude's headless call loads the CLI's own system prompt, so a short plan still reports about $0.09–0.15.
- Everything V1.4 listed as limited still applies: the edit-layer model, previews at project resolution, not tested on a physical Mac, not notarised.
